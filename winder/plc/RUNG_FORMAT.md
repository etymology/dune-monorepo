# The `.rung` language

`.rung` files are the **readable projection** of the PLC's ladder logic,
regenerated from the ACD by `uv run plc-acd-export` and compiled back to an
importable routine L5X by `uv run rung-compile`. They are what agents read
and edit; the ACD remains the source of truth at every point. See
`plans/llm-friendly-ladder-language-to-l5x.md` for the design and
`AGENTS.md` → *PLC code* for the workflow.

Scan order = top-to-bottom statement order. Each statement is a guarded
action lowering to one rung (or a small fixed group of rungs for the sugar
forms). Whatever the renderer emits is a **fixed point**: compiling it and
re-rendering reproduces the file byte-for-byte, so `git diff` after a
re-export tells you exactly whether your change landed.

## File shape

```text
routine <program>/<routine>

uses TAG_A, TAG_B            # controller scope     (generated)
uses local_x, my_timer       # program scope        (generated)
uses Local:1:I               # module I/O           (generated)

local bool new_flag                      # NEW tags this edit introduces
local motion my_move_ctl
local timer settle_timer preset 250ms
local bool scratch_bits[32]

<statements...>
```

- `uses` lines are generated by the renderer from the tag JSON exports;
  you only add `local` lines when introducing tags. Every referenced tag
  must be `uses` (existing) or `local` (new) — `rung-compile` errors
  otherwise.
- Local types: `bool int dint real motion timer counter`; arrays as
  `name[n]`; timers/counters take `preset <N>ms`. The preset is written
  into the synthesized tag's `PRE`.
- `# ...` comments are ignored by the compiler and **not preserved** by
  the next re-export — don't rely on them surviving the cycle.
- A `# PENDING EDIT in Studio` marker means the ACD holds unfinalized
  edits for that rung; `rung-compile` refuses the routine until the human
  resolves them in Studio.

## Statements

| Form | Lowers to |
| ---- | --------- |
| `<action> when <expr>` | one rung: contacts + the action |
| `<action>` | one unconditional rung |
| `when <expr>:` + indented actions | one rung: contacts + series outputs |
| `always:` + indented actions | one unconditional rung, series outputs |
| `<bool> = <bool-expr>` | contacts + `OTE` — the bit *follows* the condition every scan (writes 0 when false) |
| `<tag> = <value-expr>` | `MOV` (bare number/tag) or `CPT` (computed); only writes when the rung is true |
| `<tag> = <value-expr> when <expr>` | guarded `MOV`/`CPT` |
| `on rising <expr>:` + actions | an `OSR` rung + one gated rung per action. Bit names: when `<expr>` is a single tag, derived from it (`<slug>_osr_sb` storage, `<slug>_rising` edge); otherwise `auto_edge_<k>_sb/_ob` |
| `on falling <expr>:` + actions | same with `OSF` (`<slug>_osf_sb`, `<slug>_falling`) |
| `on entry of <bool>:` + actions | rising edge of a state-active bit; action rungs re-check the bit |
| `on rising/falling <expr> using <storage>, <edge>:` | pins the one-shot's storage and edge bits to those exact tags instead of inventing names |
| `let <name> = <expr>` | compile-time alias (not a tag); substituted into later expressions. The renderer never emits `let`. |
| `label <name>` | `LBL(name)NOP();` — jump target for `JMP(name)` |
| ``raw `...` `` | verbatim rung text (paren dialect); tag-scope check downgraded to a warning |

The distinction between the two `=` forms: an *unguarded* assignment whose
right side is boolean (`and/or/not`, a comparison, `on`/`off`) is an OTE
rung; everything else is a value write. A bare tag copy `x = y` is an
unconditional value write, which for BOOLs behaves identically to an OTE
follow.

## Expressions

`and`, `or`, `not`; comparisons `== != < > <= >=`; arithmetic
`+ - * / mod`, functions `abs sqr sin cos tan atn ln log trn`; member
access `main_xy_move.IP`; array index `bits[3]`; module I/O paths
`Local:1:I.Pt05.Data`. Normal precedence, parentheses allowed. `not` only
applies to single tags and comparisons after expansion (ladder cannot
negate a whole branch; the compiler pushes `not` inward automatically).

Uppercase instruction atoms pass straight through where no sugar exists:
`LIM(low, x, high)` or `ONS(bit)` in conditions; `MCS(X_Y, ctl, All, Yes,
10000, "Units per sec2", Yes, 1000, "Units per sec3")` as an action.
Operands containing spaces/commas are double-quoted.

## Actions

```text
NEXTSTATE = 1                          # assignment (MOV/CPT)
servo_on   X_axis using x_axis_mso     # MSO
servo_off  X_axis using x_axis_msf     # MSF
fault_reset X_axis using x_axis_mafr   # MAFR
latch ESTOP_LATCH                      # OTL
unlatch ESTOP_LATCH                    # OTU
start_timer settle_timer               # TON (preset shown as a comment)
count_up cycle_counter                 # CTU
reset settle_timer                     # RES
call xy_speed_regulator                # JSR(name, 0)
JMP(lbl_done)                          # generic instruction passthrough
```

### Motion, named-argument

```text
move_axis Z_axis using z_axis_move:        # MAM
    type     = absolute                    # or relative
    position = 0
    speed    = 1000 units/s
    accel    = 10000 units/s2
    decel    = 10000 units/s2
    profile  = s-curve                     # or trapezoidal
    jerk     = 10000                       # sets accel & decel jerk

coordinated_move X_Y using main_xy_move:   # MCLM
    type        = absolute
    target      = X_POSITION
    speed       = XY_SPEED_REQ units/s
    accel       = XY_ACCELERATION units/s2
    decel       = XY_DECELERATION units/s2
    profile     = s-curve
    termination = programmed
```

Omitted keys take the schema defaults (`src/dune_winder/rung_lang/schema.py`);
unusual fields like `command_tolerance`, `merge`, `accel_jerk`/`decel_jerk`
appear only when they differ from the defaults. Motion block actions can't
take a `when` suffix — wrap them in a `when ...:` block.

## What the compiler guarantees

- Unresolved tags, unknown motion keys, bad JSR targets, and pending-edit
  markers are **compile errors**, not Studio import surprises.
- `rung-compile` prints an equivalence report: a textual rung diff against
  the current export plus a semantic check (random-valuation simulation,
  `src/dune_winder/rung_lang/equiv.py`). "NOT equivalent" is expected
  exactly when your edit changes behaviour — review the `+`/`-` rungs.
- One-shot bookkeeping bits (`OSR`/`OSF` storage + edge) get deterministic,
  informative names derived from the trigger tag (`<slug>_osr_sb` /
  `<slug>_rising`, etc.), so the generated ladder stays readable. Existing
  hand-named bits are **preserved**: the renderer spells them out in a
  `using <storage>, <edge>` clause, so a recompile does not rename them.
  Only genuinely new blocks (no `using` clause, written by hand or by an
  LLM) get freshly invented names. The equivalence checker, not
  byte-diffing, remains the correctness bar for re-imports.
- Renaming or repacking that the compiler performs (`CMP(STATE=9)` →
  `EQU(STATE,9)`, packed multi-output rungs splitting into one rung per
  statement) is semantically checked and normalizes once, after which the
  text is stable.
